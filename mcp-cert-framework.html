01 - Certification Tiers

Three tiers scaled to privilege level

Certification requirements escalate with server privilege level and deployment model. Tier assignment is based on transport type, access scope, and data sensitivity.
L1
Sandbox
Local, read-only, stdio transport
Suites: A B C D
Review: Automated only Cert validity: 6 months Transport: stdio Examples: Context7, Serena, NX
L2
Connected
Remote HTTP/SSE, read-only external APIs
Suites: A B C D + partial H
Review: Automated + manual Cert validity: 3 months Transport: HTTP/SSE with TLS Examples: Atlassian, Sentry
L3
Privileged
Write access, PII handling, or financial ops
Suites: A B C D E F G H
Review: Automated + manual + architecture Cert validity: 3 months or on change Transport: Any (full security controls) Examples: Playwright, Filesystem (R/W)
02 - Certification Process Flow

End-to-end certification DAG

From submission to registry entry. Critical pre-scan findings stop the process immediately. Manual review applies only to L2 and L3.

05 - Execution Architecture

InfoSec-controlled infrastructure, no developer access required

The test harness runs on an isolated DigitalOcean sandbox. MCP servers are evaluated inside ephemeral Docker containers. The harness acts as a synthetic MCP client.
06 - Certification Decisions

Four possible outcomes

Every certification run produces one of four outcomes, recorded in Sentinel DB with full test results, SHA-256 tool definition hashes, and approved scopes.
CERTIFIED
All automated tests pass. Manual review clear (if applicable).
Added to approved registry. Valid for tier-specific duration (3 or 6 months).
CONDITIONAL
Minor findings that do not block safe use.
Added to registry with conditions documented. Follow-up required within 30 days.
FAILED
Critical or high findings. Unsafe for use.
Not added to registry. Remediation guidance provided. Re-submit when fixed.
REVOKED
Post-certification material change detected.
Removed from registry. Recertification required before continued use.
07 - Recertification Triggers

Six events that invalidate a certificate

Any of the following triggers removes the server from the approved registry and requires a full recertification run before the server can be used again.
Tool definition change (hash mismatch)
Server package version update
Permission scope change
New vulnerability in server or dependencies
Certification expiration reached
Manual request by InfoSec
